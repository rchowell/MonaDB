Design

MonaDB is a compiler and a virtual machine in a trench coat. Query text is lexed, parsed, lowered to an IR, compiled to bytecode, and executed against an embedded key-value store.

Stages

SQL text→ Lexer→ Parser→ IR→ Compiler→ Vop bytecode→ VM→ LMDB

Lexer

A logos DFA turns raw text into a spanned token stream. Tokens carry source ranges so errors can point back at the offending characters.

Parser

A LALRPOP LR(1) grammar consumes those tokens. Grammar rules stay thin — each action just constructs an IR value via a function in the IR module. Operator precedence and associativity are declared inline on the expression rules.

IR

The AST/IR distinguishes sum types from product types: enums for alternatives (Statement, Expr, Type) and structs for grouped fields (Select, Insert, Create). Recursive nodes are always boxed through aliases like ExprRef and TypeRef.

Compiler

A tree-walking compiler lowers the IR to a flat Vop program. Dispatch methods are prefixed cc_; small append helpers are prefixed emit_. Control-flow instructions are emitted with placeholder jump targets and back-patched once the body's size is known.

VM

A stack-based interpreter loops over the Vop program. Variables live on the stack — define(name) records a slot, and its index is how later Load instructions address it. Counters drive loop bounds for clauses like fetch.

Storage

Execution reads and writes LMDB, a memory-mapped B+tree store. There is no server process: the engine runs inside the host program.

Design principles

Thin grammar

Grammar actions only build IR. All meaning lives in later passes, not the parser.

Document-first

Objects, arrays, and JSONPath traversal are core to the model, not extensions.

Compile, don't tree-walk

Queries become bytecode so execution is a tight loop over compact instructions.

Familiar, simplified

Mostly the SQL you expect — fewer corners, document-friendly defaults.
