What Makes RQL Different

One language, four ideas
01 · Model

Documents

Objects, arrays, and path traversal are core constructs, not extensions. Schemas are optional — or absent entirely.

02 · Execution

Bytecode

Every query compiles to compact Vop instructions. The VM runs a tight loop over them instead of walking the tree.

03 · Runtime

Embedded

Backed by LMDB and run in-process. No server, no daemon, no configuration file to babysit.

04 · Surface

Familiar

The SQL clause vocabulary you already know — select, from, where, group, order — with document-friendly defaults.

02

How It Holds

Documents are first-class.

Objects, arrays, and path-style traversal live in the language model. A table can carry a full schema, a partial one, or none at all.

Compiled, not interpreted.

RQL lowers to a flat sequence of Vop bytecode. The VM dispatches one arm per opcode over a value stack — no tree-walking at query time.

The database is a library.

MonaDB links into your process and reads a memory-mapped LMDB store. There is no network hop between your code and your data.

Familiar, with fewer corners.

Most of the SQL you know carries over. What's left is smaller, more regular, and friendlier to nested data.

Get Started

Start with one line.

Clone the repo, run the REPL, and you have an embedded document database in your terminal. No server, no sign-up, no config.
